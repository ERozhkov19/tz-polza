# Архитектура для 1200 email-адресов (несколько клиентов). Дёшево и отказоустойчиво

## Цель
Есть ~1200 email-ящиков для аутрича разных клиентов/направлений. Нужно:
- распределять отправку по ящикам (ротация),
- следить за лимитами/репутацией,
- чтобы при падении одного компонента система не вставала,
- минимальная стоимость инфраструктуры.

## Компоненты
1) **Postgres (основная база)**
Храним: clients, domains, inboxes, campaigns, leads, sends, events, limits, reputation_score.
Это “истина”: кто, что, когда отправлял и с каким результатом.

2) **Очередь задач (Redis Streams или RabbitMQ)**
Задача: не отправлять “в лоб”, а выдавать задания воркерам равномерно и с ретраями.
Сообщение в очереди: `send_task = {lead_id, campaign_id, chosen_inbox_id, template_id, planned_time}`

3) **Планировщик (scheduler)**
Периодически берёт лидов из базы и кладёт задания в очередь с учётом:
- дневных/часовых лимитов на inbox,
- окон отправки (time windows),
- прогрева (warm-up),
- распределения по доменам/провайдерам,
- приоритетов по клиентам.

4) **Воркеры отправки (send workers)**
Stateless сервисы (Docker), которые:
- читают задания из очереди,
- отправляют письма через SMTP аккаунты,
- пишут результат (успех/4xx/5xx/ошибка) в Postgres,
- при ошибках делают backoff и повтор.

5) **Сбор событий (feedback)**
Минимум:
- парсинг bounce/auto-reply через IMAP (если доступно),
- запись событий в таблицу events.
На основе событий пересчитываем `reputation_score` и стопаем проблемные inbox.

6) **Мониторинг и алерты**
Метрики:
- bounce rate, 4xx/5xx rate,
- количество отправок по inbox/домену,
- ошибки SMTP connect/auth,
- “мертвые” inbox (не логинится).
Алерты в Telegram при превышении порогов.
Минимально можно начать с логов + Uptime Kuma; дальше Prometheus/Grafana.

## Ротация и распределение нагрузки
- Каждый inbox имеет лимиты (например 30–50 писем/день, + rate limit в минуту).
- Алгоритм выбора inbox:
  - берем только “здоровые” (health ok),
  - не превышаем лимиты,
  - учитываем warm-up статус,
  - равномерно распределяем по доменам/провайдерам,
  - если растут bounces/5xx — inbox в карантин.
- Нагрузка распределяется очередью + несколькими воркерами (горизонтальное масштабирование).

## Риски и как закрывать
1) **SMTP часто не подтверждает существование пользователя**
→ handshake делаем best-effort, а реальную доставляемость оцениваем по bounce/ответам/статистике.

2) **Падение репутации домена/ящиков**
→ warm-up, лимиты, автостоп при ухудшении метрик, изоляция доменов по клиентам.

3) **Single point of failure**
→ несколько воркеров; очередь + база с бэкапом; по возможности managed Postgres или реплика.

## Оценка стоимости (очень грубо)
- 2–3 недорогих VPS под воркеры: ~20–60 €/мес
- Postgres (VPS/managed): ~15–80 €/мес
- мониторинг можно держать минимальным: ~0–20 €/мес
Итого: примерно ~35–160 €/мес на старт (без стоимости самих почтовых ящиков).
